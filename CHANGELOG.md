# Changelog

All notable changes to this project are documented in this file. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The project follows [Semantic Versioning](https://semver.org/), with the 0.x caveat that the public API may change.

This repository is the Go implementation of Forgebase ([ADR 0026](docs/adr/0026-go-implementation.md)). The changelog of the Rust implementation, up to M10, is in the frozen repository <https://github.com/tvstore/Forgebase>.

## [Unreleased]

### Added

- **P5.2 The `site` commands and TLS to PostgreSQL (`internal/db`, `internal/app`, `examples/sites`, CI).** Ported from the Rust crates `forgebase-db` (`tls.rs`, `backup.rs`, `database.rs`, `connect`) and `forgebase` (`backup.rs`, the `site` commands of `run.rs`, `config.rs`), which are Rust milestones M7.2, M7.3 and M9.0 (owner: *"setuju TLS di P5"*). No new dependency.
  - Difference for the parity report: the `sslrootcert` file reader matches rustls-pki-types (`pem_file_iter`) for ordinary PEM files (text outside sections and key sections skipped; a missing or mismatched end marker or bad base64 refuses the file; an unparsable certificate ignored), but not for unusual ones: Go refuses unpadded base64, spaces inside a body line and bad base64 in an unknown section, skips a BEGIN line without exactly five dashes, accepts markers with leading whitespace, refuses an END line with trailing text, a nested BEGIN and lone `\r` line ends, where Rust does the opposite; the error details after the `tls.rs` prefix are Go's wording (`pem::Error` Display and `I/O error: … (os error 2)` in Rust).
  - **TLS ([ADR 0018](docs/adr/0018-postgres-tls.md), exactly).** No `sslmode` or `disable`: no TLS. `require`, `verify-ca` and `verify-full`: TLS with the chain **and** the host name verified by `crypto/tls` (through pgx's TLS configuration); the roots are the operating system's pool, or only the certificates of the PEM file `sslrootcert=<path>` (`system` is the system pool); an empty system pool or an unreadable file is an error that names the file or says what to install. `prefer`, `allow` and unknown values are refused with the Rust texts; `sslrootcert` without TLS, repeated keys, the other `ssl*` options, a raw `/`, `?` or `#` before the first `@`, a Unix-socket host or no host with TLS are refused as in `tls.rs`; there is no fallback to plain text; the host name is sent as SNI; SCRAM channel binding and the cancel request use the TLS connection; `sslnegotiation=direct` is passed on. The P1.2 refusal of the TLS modes ("arrives with phase P5") is gone. A handshake failure is `error performing TLS handshake: <cause>` (never a password error, never the URL or the password).
  - **`internal/db`:** `tls.go`, `CreateDatabase(ctx, url, maintenanceDB)`, `DefaultMaintenanceDB`, `PgEnvironment(url)` (`PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, `PGSSLMODE` and `PGSSLROOTCERT`; options that these cannot express are errors that name the option), `InspectDatabase` (the server version and the emptiness check, `EmptyCheckSQL`), `DatabaseInfo`, the error kinds `ErrCreateDatabase` and `ErrBackup`.
  - **`forgebase site list|create|backup|restore`** with the arguments, outputs, messages and exit codes of Rust: `list` needs no database; `create NAME [--maintenance-db NAME] [--empty]` creates the database and migrates it (refuses an existing one with exit 1; `--empty` needs no apps and no `--doctypes`); `backup NAME --out FILE` runs `pg_dump --format=custom` into `FILE.partial` (mode 0600, published with a hard link, never overwrites); `restore NAME --from FILE` runs `pg_restore --single-transaction` into an empty database. The tools are looked up in `FORGEBASE_PG_BIN` or on `PATH`, must have the server's major version, and get the connection and the TLS settings in their environment only (no `PG*` variable of the operator is passed on, no URL or password on a command line); the backup must not be newer than the server. `--site` is a usage error for the `site` commands. `site` is gone from the not-yet-ported list.
  - **CI:** the `check` job installs the PostgreSQL 16 client tools and starts `.github/ci/pg-tls.sh` (the Rust script, unchanged), so the TLS tests run in `go test -race ./...`; the new job `sites` runs `examples/sites/ci.sh` (two sites, a backup restored into a new database) and is in `needs` of `ci-result`. The workflow, webhook, custom field and user permission parts of the Rust script, and `receiver.py`, arrive with P6 and P7 (listed in the header of the script).
  - **Tests**, each with a `// Rust: file::test` comment: `tls.rs` (all the unit tests and the integration tests; the host name test runs against a fake server, see below), `inspect_database.rs`, `backup.rs` (the unit tests and the eight integration tests with the real tools), `backup_tls.rs`, and the `site list`, `site create` and `follow_ups` scenarios of `site_apps.rs`.
  - **Differences from Rust, for the parity report.** (1) The TLS error texts are those of `crypto/tls` (`x509: certificate signed by unknown authority` where rustls says `UnknownIssuer`). (2) A set `PGSERVICE` is refused by every connection, `site backup` and `site restore` included (the P1.2 deviation: pgx cannot be told to ignore it); the tools themselves never see it. (3) `hostaddr` is not supported (P1.2), so the host name test of `tls.rs` runs against a fake server that speaks the TLS start of the protocol (`internal/db/tls_fake_test.go`) instead of `hostaddr=127.0.0.1`. (4) Locally the TLS tests are skipped with a notice when the variables are missing (Rust prints a notice and passes); with `CI=true` they fail. (5) `site backup` and `site restore` name `hostaddr`, `tcp_user_timeout` and `load_balance_hosts` as unsupported options as Rust does, although the Go connection refuses them with its own message. (6) A killed `forgebase` does not stop the `pg_dump` it started, as in Rust.

- **P5.1 Background jobs, the worker, the scheduler and the built-in clean-up jobs (`forgebase`, `forgebase/testing`, `internal/db`, `internal/app`, `examples/`).** Ported from the Rust crates `forgebase` (`jobs.rs`, `worker.rs`, `job_cmd.rs`, `schedule.rs`, `builtin.rs`, `documents.rs`, `compose.rs`, `testing.rs`) and `forgebase-db` (`jobs.rs`, `schedule.rs`), which is the job part of Rust milestone M6. **The shape of the Go API is [ADR 0028](docs/adr/0028-go-public-api-of-the-app-model.md#background-jobs-and-schedules-p51), which this phase extends.**
  - **The job queue and the scheduler (`internal/db`).** `jobs.go`: `ClaimJob` (leases, oldest `run_at` first, `FOR UPDATE SKIP LOCKED`, expired leases first), the guarded `CompleteJob`, `FailJob` (retry after a delay, or dead; the error is cut to 2000 characters) and `ReleaseJob` (the attempt is not counted), `PurgeFinishedJobs` (done and dead jobs finished more than 7 days ago), `ListJobs`, `GetJob` and `RetryDeadJob`; `schedule.go`: `Spec` (`EveryMinutes`, `DailyAt`, `WeeklyOn`; UTC; every N minutes is aligned to the Unix epoch), `SyncSchedules` (add, change, keep, delete; with a dry run) and `Tick` (the due time is claimed by moving `next_run_at` in the transaction that enqueues the job, so a tick is enqueued once however many workers run; missed ticks are not caught up). `MigrateAll` is `MigrateApps` plus the sync of the schedules under the same lock (`nil` leaves the table alone, an empty list deletes all). The SQL is that of Rust, statement by statement; the migrations (0005 to 0007) were already there.
  - **The public API (root package).** `App.Job`, `App.JobWith`, `App.Schedule`; `JobHandler` (a function `func(ctx, *JobContext) error`), `JobContext` (`Name`, `ID`, `Attempt`, `Payload`, `DecodePayload`, `Enqueue`, `Documents`), `JobError` (`NewJobError`, `NewPermanentJobError`), `JobOptions` (`NewJobOptions`, `MaxAttempts`, `Timeout`, `Backoff`), `Schedule` (`EveryMinutes`, `DailyAt`, `WeeklyOn`), `Documents` (`Get`, `List`, `Insert`, `Update`, `Delete`, `Submit`, `Cancel`, `Amend`), `StoredDocument`, `ListQuery`, `FilterOp`, `DocError`, `Changes` and `DocStatus`. The composition rules and every startup message are those of Rust (a job name is a DocType name; a duplicate job; invalid options; a schedule for a job the app did not register, a second schedule, invalid values), with the Go spelling where a message names a function, plus a `nil` handler.
  - **The worker (`forgebase worker [--concurrency N]`).** Claims only the jobs of the apps installed on its site and the built-in ones; one transaction per attempt together with its completion (guarded: a lost lease rolls the handler's effects back); retries with the backoff `base * 2^(attempt-1)` up to the cap; dead after the attempts or at a permanent error; a panic and a timeout are retryable failures; the first SIGINT or SIGTERM stops claiming and lets running jobs finish for 30 seconds (then they are given back, not counted as an attempt), a second exits at once; the scheduler ticks inside it, one slot per poll interval; a pool of `N+2` connections; the log lines of Rust (`worker: started ...`, `job NAME ID done (attempt 1)`, `... failed (attempt n of m), retry in S s: ...`, `... dead after attempt n: ...`, `stopping: ...`, `stopped`). The registry is taken from one method, the seam for the live reload of custom fields (P7).
  - **`forgebase job list|show|retry|enqueue`** with the flags, output, messages and exit codes of Rust (`job show` prints the keys in alphabetical order, as `serde_json` does). `worker` and `job` are gone from the not-yet-ported list; `site` stays.
  - **`migrate` syncs the schedules** and prints `schedules: changed N` with one `add`, `change` or `remove` line each (`would change` with `--dry-run`); the stock binary stores its three built-in schedules; the schedules of an app that is not installed on the site are deleted.
  - **The built-in clean-up jobs** (app name `forgebase`, in every binary): `forgebase.purge_jobs` (daily 03:00 UTC), `forgebase.purge_login_failures` and `forgebase.purge_sessions` (every 60 minutes), in batches of 1000 and at most 100 batches per run. `forgebase.deliver_webhook` is not registered yet (P7), so the worker of a binary without apps says `3 job type(s)` where the Rust one says 4.
  - **`forgebase/testing`:** `RunJobs(binary, db)` (`JobRun{Done, Retried, Dead}`) and `RunSchedulesAt(binary, db, at)`.
  - **Examples:** `sales` registers `log_order_event` and `daily_summary` and the schedule `DailyAt(2, 0)`, `sales_extension` registers `plan_follow_up_visit`, with the handlers of the Rust example.
  - **Tests**, each with a `// Rust: file::test` comment: all of `crates/forgebase-db/tests/jobs.rs` (the queue tests that P2.1 deferred included) and `schedule.rs` (the purge tests of the auth rows too), the unit tests of `schedule.rs` (db), of `jobs.rs`, `documents.rs`, `job_cmd.rs` and `worker.rs` of the `forgebase` crate, `tests/jobs.rs`, `tests/schedules.rs`, the job parts of `app_binary.rs`, `site_apps.rs` and `sites.rs`, `cli.rs::the_worker_of_a_binary_without_app_jobs_runs_the_built_in_jobs_and_stops_on_sigterm`, and the job tests of the `sales` and `sales_extension` examples. Where a Rust test submits or cancels an order with a workflow transition (P6) the Go test queues the job with SQL and makes the order submitted with SQL; the transition halves are deferred to P6.
  - **Differences from Rust, for the parity report.** (1) A handler is a function that gets a `context.Context`, and the abort of an attempt is cooperative: Go cannot stop a goroutine, so the context is cancelled, the transaction is never committed, the connection is closed and the failure is recorded; a handler that ignores its context keeps its goroutine until it returns (documented on `JobHandler`). (2) The getters of `StoredDocument`, `JobError` and the rest are exported fields; `JobOptions` and `ListQuery` are values with chained methods. (3) A schedule's hour and minute are `int` and an out-of-range value is a startup error; the `EveryMinutes` message names the Go function. (4) `forgebase.deliver_webhook` and `Documents.Transition` arrive with P7 and P6.
- **P4 The app model and the developer experience (`forgebase`, `forgebase/testing`, `internal/app`, `internal/db`, `examples/`).** Ported from the Rust crate `forgebase` (`app.rs`, `builder.rs`, `compose.rs`, `testing.rs`, `new_app.rs`, the templates) and `forgebase-db` (`app_migrations.rs`), which is Rust milestone M5. **The shape of the Go API is [ADR 0028](docs/adr/0028-go-public-api-of-the-app-model.md)** (decided by the working session within G3; the owner can overrule it), which also maps every public item of the Rust crate to its Go counterpart or to the phase that adds it.
  - **The public API (root package `forgebase`).** `forgebase.NewApp(name)` with `Version`, `DependsOn`, `DocTypes(fs.FS)`, `Hooks(doctype, DocTypeHooks)`, `Migrations(fs.FS)` and `Name`; `forgebase.New().App(a).App(b).Run()` (and `Check`, `RunArgs`) with the composition rules of ADR 0012 (apps in order and never sorted, ownership, `DependsOn`, Links and hooks only to the app and its dependencies, hooks in app order, the `local` app of `--doctypes`, `StartupError` listing every problem, exit code 1). `DocTypes` and `Migrations` read an `embed.FS` (`//go:embed doctypes/*.toml`): every `.toml` (`.sql`) at any depth in lexical order, with the path in the file system as the name in messages; a migration file is named `NNNN_name.sql` (the version and the name of the Rust call `(1, "name", path)`). The types of a hook (`DocTypeHooks`, `BaseHooks`, `HookContext`, `HookError`, `Operation`, `TransitionInfo`, `EnqueuedJobs`, `Document`, `Row`, `Value`, `Decimal`) are type aliases of the internal types, with one-line constructors. `forgebase.Version` moved to `internal/app` (the root package re-exports it) and `cmd/forgebase` is `forgebase.New().Run()`.
  - **Composition and app migrations (`internal/app`, `internal/db`).** `compose(apps, local)` replaces the directory-only composition: the checks of `compose.rs` that M5 has (names, `local` and `forgebase` reserved, dependencies and their order, migration versions, DocType files, the Link and Table rule between apps, hooks), with every Rust message; the hint of the app-rule message names the Go call (`add DependsOn("crm"), registered before ...`). `db.MigrateApps` (and `db.Migrate`, which has no apps) applies the app migrations under the migration lock: verified before the sync (changed, removed and out-of-order migrations are refused, nothing but the framework migrations applied), then each in its own transaction with its `fb_app_migration` row and the lock timeout, `fb_app` upserted; new `db.Error` kinds for the four refusals with the Rust texts; `db.RecordedApps`. The report text of `migrate` (already in P2.2) now has lines. **Per-site `apps`** (Rust M7.2, `site_apps.rs`) is included because the config already parsed it: a site composes only its installed apps (a problem found only there names the site), `serve` composes a registry per site, and `migrate` warns about an app recorded in the database that the site does not install.
  - **`forgebase/testing`** (`testing/`): `NewDB(t)` (a throwaway `fb_test_app_*` database, dropped by `t.Cleanup`, fails and never skips without `FORGEBASE_TEST_DATABASE_URL`), `DB.Migrate`, `Exec`, `Rows`, `CreateUser`, `CreateToken`, `Client` (an in-process HTTP client: `Login`, `WithToken`, `WithoutCSRF`, `Get`, `Post`, `Patch`, `Delete`, `PostRaw`, `Reply`), and the guard `AssertDocTypesListed(t, app, dir)` that compares the DocType files on disk with the embedded set. `run_jobs` and `run_schedules_at` (P5), `check_reports` (P6) and the fixture, custom field and webhook helpers (P7) come with their phases.
  - **`forgebase new-app NAME --forgebase-path DIR [--dir DIR]`** (the `notYet` entry is gone): writes a Go module (`go.mod` with a `replace` to the absolute checkout path, the checkout's `go`, `toolchain`, requirements and `go.sum`; the app package; `cmd/NAME`; `doctypes/NAME_note.toml`, byte-identical to the Rust template; tests; `README.md`; `AGENTS.md`) that builds and passes its tests as created. Same placeholders, rules (never overwrite, a failed run leaves nothing) and messages as Rust; the Go name rules replace the Rust keyword and crate-name lists (a Go keyword, a predeclared identifier or a package of the standard library is refused). CI job **`app-template`** (generate outside the checkout, gofmt, vet, tidy, test, build, migrate, create a user, serve, log in, `"app":"demo"`), in `ci-result.needs`.
  - **Example apps** `examples/sales` and `examples/sales_extension`, each a Go module of its own (`replace` to the checkout) so that the compiler enforces the public-API boundary (reason in ADR 0028); the root module's `go.mod` and `go.sum` are unchanged and CI runs both in the job `check`. They contain the M5 parts: the DocTypes (byte-identical to the Rust files), the hooks (`OrderRules`, `MinimumOrder`, `FollowUp`), the SQL migration (byte-identical), their binaries and READMEs. **Not yet, with the phase:** jobs, schedule, the log and follow-up jobs (P5); the workflow transitions, the report (P6); the method, fixtures and the overlay (P7). The hooks that enqueue `sales.log_order_event` and `sales_extension.plan_follow_up_visit` are ported as they are; they cannot be reached until the transitions (P6) and the job registration (P5) exist.
  - **Decimal arithmetic** (`internal/decimal/arith.go`): `Sign`, `Add`, `Mul` and `Rescale`, which the hooks of `sales` need (Rust gets them from `rust_decimal`). Results that do not fit are reported, never rounded to fit (stricter than `rust_decimal`); `Rescale` to fewer digits rounds half away from zero.
  - **Tests**, each with a `// Rust: file::test` comment where it is a port: from `crates/forgebase/tests` `apps.rs` (embedded files, the guard, hooks across apps, ownership, every app migration test), `startup.rs`, `new_app.rs` and `app_binary.rs` (the app model parts: the binary is the test binary run again), the unit tests of `compose.rs` (apps), `new_app.rs` and the template placeholders; from `forgebase-db/tests/app_migrations.rs` all of it; from `site_apps.rs` the migrate, CLI and config scenarios that need no worker, site list or fixtures; from the examples' tests the hook tests, the migration, the computed amounts and the level 1 field (the lists at the top of `sales_test.go` and `sales_extension_test.go` name every Rust test that is deferred and with which phase). Where Go cannot express a Rust test (a migration listing out of order, a negative version, `./` in an embedded path) the Go test says what replaced it.
  - **Differences from Rust, for the parity report.** (1) The file-name rule for migrations and the embedded directory in place of the explicit lists (ADR 0028). (2) The hint of the app-rule startup message names the Go call. (3) Help text of `new-app` and its name errors say Go instead of Rust. (4) `RunArgs` takes the arguments without the program name. (5) The Go testing helpers fail the test with `t.Fatalf` where Rust panics, and have no `cleanup()`. (6) `Decimal` has `Add`, `Mul`, `Rescale` that report not-ok where `rust_decimal` would scale the result down to fit (this amends ADR 0027's "no arithmetic"; ADR 0028). (7) `AssertDocTypesListed` reads the directory recursively, the Rust guard only the files directly in it. (8) The generated app imports its package as `apppkg` and names its files `app.go` and `app_test.go`, so no app name that is a valid package name clashes with a template identifier (a test generates and vets a module for each risky name). The names the go command treats specially are refused: `std`, `all`, `tool`, `work`, `toolchain`, `mod`, `builtin`, `arena`, `testdata`, `main`, `cmd`, `internal`, `vendor` and the Windows device names, besides the standard-library roots, keywords and predeclared identifiers. (9) Exported members of the aliased internal types are public API (the list is in ADR 0028).
- **P3.2 The HTTP API, `serve` and the desk served by Go: the first visible result (`internal/httpapi`, `internal/app`, `desk/`).** Ported from the Rust crates `forgebase-http` and `forgebase` (`run.rs`): `forgebase serve --doctypes DIR` serves the API of P3 and the unchanged desk. Try it with the [quick start](README.md#quick-start).
  - **The HTTP API (`internal/httpapi`, standard library `net/http` only, no framework).** The request pipeline of the Rust crate: the Host selects the site first on every route and every error (`400 invalid_host` for a missing, repeated or malformed Host and, in the implicit single-site mode, for a host outside `FORGEBASE_ALLOWED_HOSTS`; `404 not_found` "no such site" with a config file; `X-Forwarded-Host` and `Forwarded` are never read; an absolute-form target must name the Host); then authentication (`Authorization: token key:secret`, which decides alone, else the `fb_session` cookie), then CSRF for a cookie request that is not `GET` or `HEAD`; the caller is always a user, never the system caller; no CORS headers; `Cache-Control: no-store` and `X-Content-Type-Options: nosniff` on every answer. Routes: `POST /login`, `POST /logout`, `GET /session` (with `X-Forgebase-CSRF: refresh`, rotates the CSRF token), `GET /meta`, `GET /meta/{doctype}` (rights, hidden fields left out, `read_only`, the workflow without its roles), `GET|POST /resource/{doctype}` (filters, sort, limit, offset, `link_titles=1`), `GET|PATCH|DELETE /resource/{doctype}/{name}` and `POST .../submit`, `.../cancel`, `.../amend`, plus `GET /desk/`, `/desk/index.html` and `/desk/assets/{name}` when a desk directory is set (strict allow-list on the raw path, the CSP, `X-Frame-Options`, `Referrer-Policy` and cache headers of the Rust desk). The session cookie is `fb_session=...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800` (no `Secure` with `FORGEBASE_DEV_INSECURE_COOKIES=1`). Every error uses the envelope `{"error": {"code", "message", "details"?}}` with the codes, statuses and bounds of the Rust `error.rs` (the message and details share 64 KiB, a string is cut to 512 characters, a list to 100 entries); this includes what the Rust axum extractors reject: a body that is not JSON content (`415 unsupported_media_type`, before the body is read), a body over the limit (`413 payload_too_large`), bad JSON (`400 bad_request`; invalid UTF-8, a lone surrogate escape, trailing text and a nesting of 128 levels are refused as serde_json does), a path parameter that is not UTF-8 after percent-decoding (`400 bad_request` "invalid path", after authentication) and a query that cannot be used (`400 invalid_query`). A body is read after authentication and before the path and the query are looked at, as the Rust extractors order it. Internal errors, and a panic in a handler, are logged to standard error and answered with the generic `500 internal`. The routing follows axum: the raw path is matched (no cleaning, no redirect of a trailing slash, `%2F` stays inside a segment, a parameter is a whole segment: it may be empty when a `/` follows it, as in matchit, so `/resource//x` is the route of the name and `/resource/x//submit` reaches submit, but an empty last segment finds no route), an unknown path is `404 not_found` "no such route", a known path with another method is `405 method_not_allowed` with `Allow`, and a `HEAD` is answered by the `GET` handler. A login over `MaxConcurrentLogins` (at most half the pool) is `503 too_many_logins` with `Retry-After: 1`.
  - **Routes of later phases are not added now** and answer `404 not_found` like any unknown path: `POST .../transition`, `GET .../transitions`, `GET .../history` (P6), `/views` and `/summary` and `/report` (P6), `/export` and `/import` (P7), `/method` (P7), `/customize` and `/user-permissions` (P7). The `AppConfig` settings of those routes (export and import limits, the metadata reload interval) and the live reload of custom fields (`RegistryHolder`, P7) come with them: `httpapi.NewStateFunc` takes the registry as a function that is called once per request, which is the seam.
  - **`forgebase serve`** (the `notYet` entry is gone): the sites of the config file (every site, or the one `--site` names) or the implicit `default` site for `FORGEBASE_ALLOWED_HOSTS`; `FORGEBASE_LISTEN` (default `127.0.0.1:8000`), `FORGEBASE_DEV_INSECURE_COOKIES=1`, `FORGEBASE_DESK_DIR` (must hold an `index.html`). It prints `listening on http://ADDRESS`, one `site NAME: HOSTS` line per site and `serving the desk from DIR at /desk/`, with the Rust warnings and error texts, and does not run migrations. The first SIGINT or SIGTERM stops accepting connections and gives the running requests 10 seconds; a second signal, or the end of the 10 seconds, exits at once. A closed standard output or standard error does not stop the server (Go ends a process that writes to a broken pipe on those descriptors unless `SIGPIPE` is ignored, which `serve` does on Unix; a test pins it).

(3) Response header names are in canonical case (`Set-Cookie`, `Content-Type`), the Rust server writes them in lower case; HTTP header names are case-insensitive. (4) The server has a 30 second limit for reading the request header, counted from the accept of a new connection or, on a kept-alive connection, from the first bytes of the next request (axum::serve with hyper sets no timer, so Rust has none); this is a deliberate deviation. (7) `Content-Length` and `Date` are written by `net/http`.
